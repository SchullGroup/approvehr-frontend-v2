# 0002 — The payroll engine exists once, in the backend

- **Status:** Proposed
- **Date:** 2026-08-21
- **Decided by:** kene (author of aabf384a; acceptance pending)
- **Scope:** both
- **Supersedes:** —
- **Superseded by:** —
- **Enforced by:** review only. Nothing stops a second engine being added. Related checks: backend `engine.test.ts` and `payroll-quote.test.ts` (what the one engine answers, and that a caller cannot supply bands); frontend `npm run verify-payroll` (the demo fixture reconciles; its cross-repo band check currently skips, see Consequences).
- **Backfilled:** 2026-10-11 from HANDOVER.md § "The payroll engine exists ONCE" and § "The frontend engine is gone"; decision dated by aabf384a (frontend, 2026-08-21 19:09 UTC)

## Context

Nigerian PAYE, pension and NHF were computed twice. The backend's `payroll/engine.ts` (21db4ad,
2026-08-20) calls itself "the authoritative implementation": integer kobo, dated `TAX_SCHEDULES`,
a relief regime that rides on the schedule. The frontend had its own preview copy in floating-point
naira from its first commit (32aad96c, 2026-08-20). By 21 August it served four preview screens:
`/settings/payroll`, `/people/new`, `/people/[id]` and the loan application.

On 2026-08-21 the backend gained the Nigeria Tax Act 2025 bands (3728e08) and the frontend copy was
left on the 2011 ones. The commit that found it, d8cac84a, records the result: all four screens
quoted ₦63,266.67 on ₦500,000 a month where the answer is ₦63,950.00, and the loan screen "tells
somebody what will land in their account". That commit first ported the new bands and added a
cross-repo guard, noting that HANDOVER "had said for a long while" the copy should go because "two
implementations of tax law is one too many". Later that day aabf384a deleted it. The commits record
wrong figures on four screens; they do not record any loss beyond that.

Deleting it needed an endpoint: `GET /payroll/preview` takes an employee id, and a salary being
typed or settings not yet saved have none. 1504fe4 (backend, 19:08 UTC) added `POST /payroll/quote`,
whose router comment says the browser copy "drifted onto last year's bands and quoted them for a
while".

## Decision

All statutory payroll arithmetic runs in `approvehr-backend:src/modules/payroll/engine.ts` and
nowhere else, including in the frontend and in offline mode. The frontend asks the API
(`POST /payroll/quote`, `GET /payroll/preview`, `GET /pay-components/preview/:id`, and the public
`POST /payroll-calculator` for the marketing page) and renders what comes back. A caller may choose
the company's settings but never the tax bands, which come from the period. Remittance schedules
sum stored payslips and do no tax arithmetic of their own (`payroll/statutory.ts`).

With no API, the demo shows fixed payslips generated by that engine
(`src/lib/mock/demo-payslips.ts`, from `approvehr-backend:scripts/emit-demo-payslips.ts`),
labelled illustrative, and refuses for a salary or settings it has no row for. It never estimates.

## Consequences

- **Easier:** a Finance Act is one dated entry in `TAX_SCHEDULES`. A payslip, a remittance schedule
  and the public calculator cannot disagree about the same person. `payroll-quote.test.ts` pins
  both incident figures (₦63,950.00 under the 2025 Act, ₦63,266.67 for December 2025) through one
  code path.
- **Harder:** every preview needs a reachable API and `VIEW_SALARIES`, and has to guard against a
  stale answer sitting beside an input that has moved (`usePayslipQuote`). Offline previews are
  omitted, and offline payroll is fixed figures for the seeded salaries only.
- **Accepted:**
  - Statute still appears in the frontend as data and copy. `STATUTORY` (the pension and NHF
    floors) is defined in both `src/lib/payroll/settings.ts` and the backend engine, and no check
    ties them together. The marketing PAYE page hard-codes the band table and a `× 0.025` in an
    explanatory sentence, which the guard does not read.
  - `verify-payroll`'s band-for-band comparison looks for the backend at
    `../../../approvehr-api` from `scripts/`. That path does not exist beside a checkout laid out as
    `approvehr-frontend-v2` next to `approvehr-backend`, and CI checks out only this repo, so the
    comparison skips with a message everywhere today. What it checks is that the fixture
    reconciles in exact integer kobo, and that every demo salary has a row.
  - The rule is held by review and by HANDOVER, not by a gate.
- **Revisit if:** the product must produce authoritative payroll figures with no API reachable,
  which today it answers with labelled fixed figures, or the demo is retired and the fixture with it.

## Alternatives considered

- **Keep the frontend copy and guard it against the backend.** Tried first, in d8cac84a: the
  guard only runs for somebody with both repos checked out, because the frontend's CI clones one
  repo. Replaced by deletion hours later.
- **Omit payroll offline.** HANDOVER: right for a preview, wrong for the module that carries the
  pitch, since a payroll product with an empty payroll module in a room with no database does not
  get bought. So previews are omitted and the demo run shows labelled fixed figures.

No other alternatives were recorded.
